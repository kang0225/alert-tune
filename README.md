# alert-tune

**과거 장애에 Prometheus 알람 규칙을 다시 돌려 보고, 설정을 튜닝해 주는 CLI**

alert-tune은 과거 메트릭과 장애 기록에 알람 규칙을 재생해서 백테스트해요.
규칙마다 탐지한 장애 수, 탐지까지 걸린 시간, 오탐을 채점하고, 정해 둔 오탐 한도 안에서 장애를 가장 빨리 잡는 임계값과 `for:` 기간을 추천해요.

> **상태:** 초기 개발 단계예요.
> 현재 버전 출력 명령과 규칙 YAML 파서를 구현했어요. 아래 백테스트·튜닝 흐름은 계획한 설계예요.
> 진행 상황은 [로드맵](#로드맵)을 참고하세요.

## 왜 필요한가요

알람 튜닝은 대부분 감으로 해요.
`for:`를 줄이면 장애를 더 빨리 잡지만 오탐 호출도 늘어나고, 어느 쪽으로 잘못 맞췄는지는 몇 주 뒤에야 알게 돼요.
alert-tune은 머지하기 전에 이 균형을 실제 데이터로 다시 돌려 봐서, 숫자를 보고 정할 수 있게 해줘요.

## 동작 방식

```
규칙 + 장애 기록 + 메트릭
  → 수집 → 신호 계산 → 재생 → 채점 → 튜닝 → 보고
```

1. **수집:** 규칙을 파싱해서 식에 쓰인 시계열만 Prometheus 호환 API(Prometheus, Thanos, Mimir)에서 받아 로컬에 캐시해요.
   그다음부터는 오프라인에서 몇 번을 돌려도 같은 결과가 나와요.
2. **신호 계산:** 비교 부분을 뺀 식(`error_ratio > 0.05` 대신 `error_ratio`)을 평가 주기마다 한 번만 계산해 둬요.
   그래서 임계값을 바꿔 볼 때마다 메트릭을 다시 조회하지 않아도 돼요.
   PromQL 엔진은 `promtool`처럼 바이너리에 내장해요.
3. **재생:** `for:`와 `keep_firing_for`를 포함해 규칙 엔진의 pending → firing → 해제 흐름을 그대로 따라가요.
4. **채점:** 장애 중에 알람이 울리면 탐지, 끝까지 안 울리면 놓침, 장애 구간 밖에서 울리면 오탐이에요.
   오탐은 주당 횟수로 보여줘요.
5. **튜닝:** 정상 트래픽의 상위 분위수(P99, P99.9 등)로 임계값 후보를 잡고, 여러 `for:` 값과 조합해 시험해요.
   오탐 한도를 넘는 조합은 버리고, 남은 것 중 놓친 장애가 가장 적고 가장 빨리 잡는 설정을 골라요.
   장애를 한 건씩 빼고 고른 설정이 빠진 장애도 잡는지 확인해서, 몇 건에만 맞춘 설정이 나오지 않게 해요.
6. **보고:** 현재 설정과 추천 설정을 나란히 보여주고, 바로 적용할 수 있는 YAML diff를 출력해요.
   GitHub Action으로 돌리면 결과가 PR 코멘트로 달려요.

장애 기록은 처음엔 간단한 YAML 파일(시작, 종료, 유형)로 넣고, 나중에는 PagerDuty에서 가져올 수 있게 할 예정이에요.

## 사용 예시 (예정)

```console
$ alert-tune sweep rules/ --incidents incidents.yml --fp-budget 1/w
OrdersHighErrorRatio
  current      > 0.05  for 2m   8/9 detected · median 3m10s · 0 FP/week
  recommended  > 0.04  for 1m   9/9 detected · median 1m40s · 0.6 FP/week
```

현재 설정(current)과 추천 설정(recommended)마다 탐지한 장애 수, 탐지 시간 중앙값, 주당 오탐(FP)을 보여줘요.
출력 형식은 예시이며 바뀔 수 있어요.
